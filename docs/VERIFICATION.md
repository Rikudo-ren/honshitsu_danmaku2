# 検証

**何を確認済みで、何が未確認かを分けて書く。**
確認していないことを「動く」と書かないための文書である。

## 検証の道具

| コマンド | 何を確かめるか | 所要 |
|---|---|---|
| `node tools/validate-assets.js` | 素材・ライセンスの整合 | 数秒 |
| `node tools/validate-music.js` | 楽曲データの構造 | 数秒 |
| `node tools/test-patterns.js` | 全 21 パターン × 3 難易度を回避 AI に 20 秒ずつ生存させる | 約 3 分 |
| `node tools/test-fairness.js` | ボスの最小距離の不変条件を狙い撃ちで検査（**240 通り**） | 約 2 秒 |
| `node tools/test-input.js` | 入力（キー割り当て・タッチのドラッグ・集中モード・画面内ボタン）を**本番コードにイベントを流して**検査（**74 件**） | 約 1 秒 |
| `node tools/test-flow.js` | タイトル → 章 → 戦闘 → クリア → リザルト → リトライの**流れ**と BGM を本番コードで検査（**52 件**） | 約 4 秒 |
| `node tools/playthrough.js --runs N` | 全 4 章 × 3 難易度を**最後まで通してクリア**させる | 章×難易度あたり約 40 秒 |
| `node tools/render-frames.js` | 実フレームを PNG 49 枚に描き、明度・弾数を検査 | 約 100 秒 |
| `node tools/render-audio.js --sfx` | 楽曲 10 曲と効果音 24 種を**実際に波形計算**して、無音・クリップを検査 | 約 25 秒 |
| `node tools/run-tests.js` | 上記の速いものをまとめて実行（`--full` で重いものも） | — |

検証はすべて **Node + `@napi-rs/canvas`** で動く。
ゲーム本体のコード（入力・移動・当たり判定・パターン・フェーズ進行）を
そのまま読み込んで走らせるので、検証用に別実装を用意してはいない。
回避 AI（`tools/dodger-ai.js`）は**ゲームの入力系を通して**操作する。


21 パターン × 3 難易度 = 63 通りを、それぞれ 20 秒間 AI に回避させている。
**63 件すべてで AI が生存した。** 弾速はすべて上限以内
（EASY 301 / NORMAL 341 / HARD 373 px/s 以下）であることを毎フレーム検査している。

AI が被弾したパターンは 2 件だけだった（HARD の `laserBoundary` 8.4 秒、
HARD の `chaserMie` 10.1 秒）。被弾しても残機があるため生存判定は OK である。
残りの 61 件は無傷で 20 秒を抜けた。

### 2. 公平性の不変条件 — **240 件 / NG 0 件**

`tools/playthrough.js` は「実際に遊べるか」を見るが、ボスの最小距離のような
レアケースは回避 AI の偶然の立ち回りに依存してしまう。
そこで**自機を意地悪に動かして狙い撃ちで検査**する専用の検証を用意した。

```
公平性の不変条件を直接検査した
  ボスの最小距離 140px（猶予 0.6 秒後から判定）
  自機の動かし方 5 種 × 全 4 章 × 全フェーズ × 3 配置
  合計 240 件
すべての条件でボスは 140px より近づかなかった
```

自機の動かし方は「停止 / ボスへ突っ込む / 画面端を這う / 境界 y=H*0.50 を跨いで往復 /
乱数で歩き回る」。とくに「画面端を這う」は、ボスの可動域の外側に自機が居るため
**最も条件が悪い**（縦距離しか使えない）。

この検査で実際に不具合が 1 件見つかった。自機が 1 フレームで 16px を超えて動いた場合
（被弾後の復帰位置など）は猶予をリセットするようにして直している（下の表を参照）。

抜けられる**（これが HARD の設計意図である）。

この検証は次の不変条件も同時に検査しており、違反があればその場で例外を投げる:

- 弾速が `speedCap` を超えないこと（超えたら NG）
- 同時弾数が `maxBullets = 1400` を超えないこと
- 弾の座標が `NaN` / `Infinity` にならないこと
- **ボスが自分から自機へ近づきすぎないこと**（後述）

#### 回避 AI について（この数字をどう読むか）

- AI は**ゲームの入力系を通して操作する**。移動・当たり判定・フェーズ進行は本番コード。
- ただし AI は人間ではない。**先読みして隙間を抜ける**のは得意だが、
  弾幕ゲームの定石（わざと弾を引きつける・端で待つ）は人間ほど上手くない。
- 観測（唯一の干渉手段）はゲージが溜まらないと撃てない。かすりを狙わない AI は
  ほとんど撃てない（上表の「観測」列）。**人間はここで AI より有利**になる。
- したがって「HARD 第 1 章を残機 0 で抜けた」は、
  「人間にもこのくらい厳しい」ではなく「**AI でも抜けられる**」の意味で読むのが正しい。
- なお、この 24 走は入力・HUD・BGM まわりを直す**直前**のコードで実行している。
  その修正（章の導入の進行、ポーズの Esc、練習の曲、タッチ UI）は
  `playthrough.js` が通らない経路にしか触れていないため、結果には影響しない。
  ゲーム本体に触れた修正を入れた後は、`npm test` と各検証を個別に再実行して確認している。

### 4. 入力 — **74 件 / NG 0 件**

`tools/playthrough.js` と `tools/test-patterns.js` は**回避 AI** を走らせるため、
本番の入力クラス（`src/core/input.js`）を通らない。
つまり「キー割り当て」「タッチのドラッグ」「集中モード」は、
どの検証にも当たっていなかった（ここが壊れると絵も弾幕も正常なまま**遊べなくなる**）。
そこで、登録されたイベントリスナーを実際に呼ぶ検証を用意した。

```
■ キーボード                … 13 キー（矢印 / WASD / Shift / Z / X / Esc / P / R / F / M / Tab）
■ 集中（低速）モード         … Shift で入る／離すと戻る
■ タッチ / ポインタ          … ドラッグ・差分・タップ決定・2 本目の指・拡大表示時の座標変換
■ 入力 → 自機の移動          … 本番の Player を動かして方向と距離を確認
■ 画面内ボタン              … 観測／ポーズの判定・ドラッグと決定に化けないこと
```

検証の途中で**実際に不具合が 1 件見つかった**。
`focusHeld()` が `if (ptr.down && !ptr.isTouch) return false; return false;` となっており、
**タッチでは集中モードに入る手段が存在しなかった**（ドキュメントには「ドラッグ中は常時低速」と
書いてあったのに、コードは 1.0 倍のままだった）。
タッチ用に「ドラッグ中の 2 本目の指＝集中」を実装し、上記の検証で固定した。

**タッチ端末用の画面内ボタンを追加した。** スマホには X キー（観測）も Esc（ポーズ）も無く、
このままではモバイルで「唯一の干渉手段」が使えず、中断もできなかった。
右下に観測ボタン（ゲージの溜まり具合を円弧で表示）、左下にポーズボタンを置き、
ポーズメニューは項目を**タップで選べる**ようにした。
座標は `HUD.buttonRects()` の 1 箇所で定義し、描画と判定がずれないようにしている。

### 5. 画面遷移と BGM — **52 件 / NG 0 件**

`tools/playthrough.js` は「ステージをクリアできるか」しか見ないため、
**メニューの流れ**（タイトル → 難易度 → 章 → 開始 → クリア → リザルト → リトライ）と
**BGM がいつ鳴るか**は、どの検証にも当たっていなかった。
`tools/test-flow.js` は本番の入力にキーイベントを流し、本番の `Game.frame()` を回して
実際にメニューを操作する。BGM は鳴らさずに「鳴った曲」だけを記録して照合する。

```
■ 起動 → タイトル                ■ タイトル → 難易度 → 章 → 開始
■ 章の導入（会話）→ 戦闘開始      ■ ポーズ（Esc で開閉・時間が止まる）
■ フェーズ進行と BGM の切り替え   ■ リザルトからの戻り
■ ゲームオーバーとリトライ        ■ 練習モード（フェーズ単体）
■ 最終章 → ALL CLEAR              ■ 保存（localStorage）
```

**この検証で見つかった不具合が 3 件ある。すべて修正して、上の 52 件で固定した。**

| 症状 | 原因 | 直し方 |
|---|---|---|
| **章の導入で固まる（重大）** | 扉と会話の経過時間を数える `phaseStateT += dt` が `updateIngame` の中にしか無く、`stageintro` では `updateIntro` しか走らない。扉の 2.4 秒が永久に終わらず、**新規データで章を始めると扉の画面から先に進めなかった** | `updateIntro` の先頭で `phaseStateT += dt` する |
| ポーズ中に Esc で再開できない | ポーズを**開く**側は `pause || esc` を見ているのに、**閉じる**側が `pause || cancel` だけだった。画面には「P / Esc で再開」と書いてあった | 閉じる側にも `esc` を入れる |
| 練習モードで常にボス曲が鳴る | 練習の `phaseList` は 1 枚だけなので「最後のフェーズ」判定が常に真になっていた | 練習中は章の本当の最終フェーズかどうかで判定する |

この 3 件は**絵も弾幕も正常に見える**ため、フレーム描画でもパターン検証でも見つからない。
「遊ぶ順番で通す」検証を足したことで初めて出てきた不具合である。

BGM については、章のクライマックス（最終フェーズ）でボス曲（第 4 章は `final`）へ、
章の導入（扉・会話）では静かな曲へ切り替わることも、この検証で固定している。
`playSong()` はクロスフェードを持たないため、切り替えの瞬間だけ音楽を絞って戻す
（唐突にブツ切れるのを避ける）処理を `game.switchSong()` に置いた。

### 8. 音声の波形検査 — **楽曲 10 曲 / 効果音 24 種すべてで音が出ている**

音を出す手段が無い環境なので、**Web Audio のサブセットを自前で実装し、
実際に波形を計算して数値で確認**している（`tools/render-audio.js`）。

```
曲         peak      rms       clip   無音最長
title     -14.2 dB  -22.2 dB    0     0.5%
stage1    -14.4 dB  -22.9 dB    0     0.5%
stage2    -13.0 dB  -22.6 dB    0     0.5%
stage3    -13.3 dB  -22.0 dB    0     0.5%
stage4    -12.1 dB  -22.1 dB    0     0.5%
boss      -12.7 dB  -22.4 dB    0     0.5%
final     -11.9 dB  -22.4 dB    0     0.5%
clear     -13.4 dB  -23.1 dB    0     0.5%
quiet     -17.5 dB  -26.4 dB    0     8.1%
menu      -16.6 dB  -24.8 dB    0     0.5%
```

- **クリップ 0 サンプル。** どの曲も peak が -11.9〜-17.5 dB に収まっており、
  マスターのコンプレッサが機能している（歪みがない）。
- RMS は -22〜-26 dB。BGM として適正な範囲。
- 無音区間は最大 8.1%（`quiet` は静かな曲なので意図どおり）。
- 効果音 24 種もすべて peak -10〜-32 dB で音が出ている。
- ゲーム側が呼んでいる効果音名 **20 種すべてが定義済み**であることも確認した
  （存在しない名前を呼ぶと無音になるが、そういう typo は無い）。

**但し書き:** これはブラウザの Web Audio そのものではなく、
`audio.js` が使う API だけを実装した**近似**である（リバーブは
ConvolverNode の畳み込みではなく Schroeder 型で代用、FM 変調は省略）。
したがって**「鳴っている・割れていない」ことは数値で確認できるが、
実際の聞こえ方は未確認**である。この WAV は `_work/audio/` に出力される。

## 到達するまでに直した不具合（記録）

検証は「通った」ことより「何が落ちたか」のほうが役に立つので残しておく。

| 症状 | 原因 | 直し方 |
|---|---|---|
| HARD の最終盤が 8 回中 3 回しか生存できない | `denseFinale` が `countMul`(1.42) × `intervalMul`(0.78) × 1.28 の**三重取り**になっていた | HARD を 1.0 に（1.28 は EASY を軽くするためだけの係数にした） |
| 第 1 章フェーズ 4 で追尾弾と輪が重なって詰む | 追尾弾が最後まで残り、「輪の内側」だけが逃げ道になっていた | `ringsNavy` を `until: 10, ivMul: 1.7` に。密度が上がる時間帯には追尾弾が残らない構成にした |
| ボスが自機の真上に降りてきて**出現即直撃**になる | ボスの位置から弾が生まれるパターン（`ringsNavy` / `chaserMie` / `contourWaves`）があるため | ボスの最小距離の不変条件を実装（下記） |
| 回避 AI が追尾弾で死ぬ | AI が追尾・曲線弾を**直線と仮定**して予測していた | `_project()` を実装し、ゲーム本体の弾挙動テーブル（`HN.BEHAVIOR`）を再生して予測するようにした |
| ボスの最小距離の検査が**幾何学的に満たせない**値を要求していた | 可動域が `y ∈ [H*0.12, H*0.42]` しかなく、自機が `y ≒ H*0.45` に居るとき 170 px を確保できない | 下限を 140 px に、判定を「自機が `y > H*0.50` に居るとき」に変更。可動域から最大縦距離 182.4 px を計算し、42.4 px の余裕があることを確認した |
| HUD の「残り」ラベルが秒数と重なっていた | ラベルと数字を**同じ y に右寄せ**で描いていた | 縦積みの順序を固定（ラベル y=8 / 秒数 y=20 / バー y=58 / PHASE y=66） |
| **ボスが弾より手前に描かれていた** | コードのコメントには「ボスは弾の奥に立たせる」と書いてあるのに、実際は `boss.draw()` を弾の描画の**後**に呼んでいた。ボスの体と、その後ろに敷いている暗い下地（alpha 0.62）が弾を隠し、**見えない弾に当たる**状態だった | 描画順を 背景 → ボス → 弾 → 自機 → エフェクト に修正。弾の視認性はボスの見栄えより優先する |
| フェーズ移行のカメラが動かなかった | カメラ状態を `boot()` で初期化していた。`boot()` を呼ばずに Game を組み立てる検証環境では未定義になる | `constructor` に移した（状態は boot ではなく constructor の仕事） |
| かすりの音が BGM に埋もれていた | 効果音のゲインが 0.05 と小さすぎた | 0.11 に（かすりは 1 弾につき 1 回しか鳴らないので増やしても煩くならない）。残り 10 秒の警告も 2 回鳴らすようにした |
| **章の導入（扉・会話）から先に進めなかった** | 扉と会話の経過時間 `phaseStateT += dt` が `updateIngame` の中にしか無く、`stageintro` では `updateIntro` しか走らない。扉の 2.4 秒が永久に終わらなかった | `updateIntro` の先頭で `phaseStateT` を進める。**新規データで章を始めると固まる**不具合だった（`tools/test-flow.js` が発見） |
| ポーズ中に Esc で再開できなかった | 開く側は `pause \|\| esc` を見ているのに、閉じる側は `pause \|\| cancel` だけだった（画面には「P / Esc で再開」と書いてある） | 閉じる側にも `esc` を入れた |
| 練習モードで常にボス曲が鳴っていた | 練習の `phaseList` は 1 枚だけなので「最後のフェーズ」判定が常に真になっていた | 練習中は「章の本当の最終フェーズか」で判定する |
| 章のボス曲（`songBoss` / 'boss'・'final'）が一度も鳴らなかった | 曲は定義されているのに、再生側が章の曲しか指名していなかった | 最終フェーズでボス曲へ切り替える。切り替えの瞬間だけ音楽を絞って戻す（`game.switchSong()`）。`tools/test-flow.js` で順番を固定 |
| タッチでは集中（低速）モードに入れなかった | `focusHeld()` が `if (ptr.down && !ptr.isTouch) return false; return false;` になっており、タッチの分岐が死んでいた（説明には「ドラッグ中は常時低速」と書いてあった） | ドラッグ中の 2 本目の指で集中モードに入るようにした。`tools/test-input.js` で固定 |
| タッチ端末では観測もポーズも使えなかった | スマホには X キーも Esc も無いのに、画面内にボタンが無かった | 右下に観測ボタン、左下にポーズボタンを追加。ポーズメニューは項目をタップで選べる |
| HARD の通し検証で 24 走中 3 走が最終盤で落ちていた | 回避 AI がかすりを取らないため、観測ゲージが一度も溜まらず**唯一の干渉手段を使えない**まま戦っていた（人間より弱い条件で判定していた） | AI に「当たらない範囲で弾に寄る」評価を足した。24 走すべて STAGE CLEAR になった |
| 途中の不具合: フェーズ移行直後に検査が誤検知していた | 猶予なしに距離を検査していた | ボスの退避は 1 フレーム 6 px なので、0.6 秒の猶予後にのみ判定するようにした（最悪ケースでも 0.28 秒で合法位置に戻れる） |

### ボスの最小距離の不変条件（現在の仕様）

```
自機が y > H*0.50（画面下半分）に居るとき、
ボスは中心間距離 140 px を下回らない。
退避は 1 フレーム最大 6 px（= 360 px/s）で、瞬間移動にはならない。
```

- ボスの可動域は `x ∈ [W*0.16, W*0.84]`, `y ∈ [H*0.12, H*0.42]`。
  自機が `y = H*0.50` に居るときの縦距離の最大は `H*0.50 - H*0.12 = 182.4 px` なので、
  **140 px なら常に 42.4 px の余裕がある**（満たせない下限は設定しない）。
- 自機が自分から画面上部へ突っ込むのはプレイヤーの選択なので制限しない
  ——「上に行くほど危険」は弾幕ゲームの基本の駆け引きである。
- 実装は `src/game/boss.js`、検査は `tools/playthrough.js`
  （`boss.lastDist` を**ボスの移動直後**に記録し、猶予後にのみ判定する。
  自機が動いた結果の接近は判定対象にしない）。
